# GuestOps AI 製品化アーキテクチャ（2026-11-01）
## 固定方針
- OTAの正本は顧客既存のPMS（Beds24優先、次にAirHost）。GuestOps AIはOTAの代替チャネルマネージャではない。
- 顧客にGmailアカウント追加、GAS新規作成、コードの貼付、Googleカレンダー新規作成を要求しない。
- 初期導入は管理画面でPMSを選択 → 公式権限付与・招待コード交換 → 対象施設選択 → 予約・在庫の読み取り診断 → 明示承認後に限定機能を有効化。
- PMS認証情報は顧客単位に隔離・暗号化し、データの混線を防止。顧客の予約データを他顧客に提供しない。
- Gmailからの予約メール収集は葛西の移行調査／限定的な障害診断用途だけ。製品の標準連携には含めない。
- カレンダーは清掃チーム等から明示希望がある場合のみ任意OAuth接続する。Gmailメールボックス全体の権限は標準導入に不要。
- 予約者へのメッセージ送信はPMS/OTAの対応する公式経路を優先。API未対応なら機能未提供と明示し、メール等の代替経路は顧客に個別選択させる。
- 価格更新・予約変更・既存OTA接続変更はread-only照合を完了するまで無効。設定変更は別途施設別承認を要求する。
- 顧客にAPIトークンをメールやチャットへ送らせない。公式の権限付与画面もしくはログイン済み安全な連携画面を利用する。
- 開発用GAS `GuestOpsAI_Beds24_V2_TEST` は製品配布用ではない。恒久的な顧客GAS導入を禁止する。
## 実装上の構成
1. Web管理画面（顧客、施設、権限、接続診断、監査）。
2. サービス側バックエンド（PMS adapter、予約同期、重複排除、状態差分、ジョブキュー、障害検知）。
3. 顧客単位の秘密情報保管・トークン更新。ローテーション、失効、接続解除を管理。
4. 正本の読み取り→安全診断→顧客承認→最小権限での機能解放。
5. 監査ログ（同期日時、PMS、施設ID、予約番号の内部参照、変更前後、失敗時の再試行）。不要な個人情報を永続保存しない。
## 人間操作の上限目標
- 通常顧客：既存PMSへのログインとAPI権限付与、施設の選択、運用モードの承認。Gmail・GAS操作0回を目標（現時点では設計目標で、実機検証未了）。
- 既存OTA・旧iCalの切替が必要な顧客：予約・在庫照合後、既存同期経路を変更するために管理権限と個別承認が必要。
